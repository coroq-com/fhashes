# fhashes

Web システムのサーバーのファイルのハッシュを定期的に記録し、侵入や改ざんが疑われるときに「いつ・何が変わったか」を後から調べるためのツールです。

> **試験段階です。** 設定やスナップショットの形式は、予告なく変わることがあります。

例えば次のような問いに答えます。

- 脆弱性の公表からパッチ適用までの間に、意図しないファイルの変更はなかったか
- 見つかった不審なファイルは、いつ現れたか。同じ頃にほかに何が変わったか
- このファイルは、いつからこの内容か

## 仕組み

```
監視対象のサーバー（記録する側）
  毎時 fhashes record
    全ファイルのパスとハッシュの一覧（スナップショット）を作り、rclone でストレージへ送る
        │
        ▼
ストレージ（S3 / GCS / Azure Blob など。書き換え・削除できない設定にする）
        │
        ▼
調べる側（どのマシンでもよい）
  fhashes review web1 [--from …] [--to …]
    必要な期間のスナップショットを取ってきて、前後を比べて変化を表示する
```

- 記録するのは、ファイルの内容のハッシュ（SHA-256）です。ファイルの中身そのものは送りません。
- 中身を読んでハッシュを計算するのは、ctime・サイズ・inode が前回と変わったファイルと、全体の約 1/24 だけです。24 回の実行で、すべてのファイルが一度は読み直されます。
- ストレージを書き換え・削除できない設定（WORM）にしておけば、監視対象が乗っ取られても、それまでの記録は消せません。
- 調べる側は何も保存しません（ダウンロードしたスナップショットをキャッシュするだけです）。
- 通知はしません。必要になったときに記録をさかのぼって調べるためのツールです。

設計と、その理由は [DESIGN.md](DESIGN.md) にあります。

## 必要なもの

- Python 3.9 以上と PyYAML（`apt install python3-yaml` / `dnf install python3-pyyaml`）。pip は使いません。
- rclone **1.61 以降**（apt / dnf で入るものは古いことがあるので、[rclone.org](https://rclone.org/downloads/) の単体バイナリを勧めます）。送り先の設定（下の「ストレージ」）は事前に済ませておきます。rclone の設定ファイルは `config/rclone.conf` に置くことを勧めます。

## コマンド

| コマンド | 使う場所 | 説明 |
|---|---|---|
| `bin/fhashes record` | 記録する側 | ファイルを調べてスナップショットを作り、送信待ちのものと一緒にストレージへ送る |
| `bin/fhashes review <host> [--from …] [--to …]` | 調べる側 | 1 台のホストについて、期間内の変化と監視の状況を表示し、判定を出す |
| `bin/fhashes status` | 調べる側 | ホストごとの最新のスナップショットと、直近の間隔の乱れ・異常を表示する |
| `bin/fhashes clean` | 調べる側 | ダウンロードしたスナップショットのキャッシュを消す |

`-v` を付けると詳しいログを出します。どのコマンドも `--config` で設定ファイルを指定できます。

## ファイルの置き場所

設定・状態・キャッシュは、既定ではすべて clone したディレクトリの中に置きます（`/etc` やホームディレクトリには置きません）。

```
<clone したディレクトリ>/
  config/record.yaml     記録する側の設定（docs/record.sample.yaml をコピーして書く）
  config/review.yaml     調べる側の設定（docs/review.sample.yaml をコピーして書く）
  data/record/           記録する側の状態（state.sqlite3、送信待ちの outbox/ など）
  data/cache/            調べる側がダウンロードしたスナップショットのキャッシュ
```

- `config/` の下と `data/` は git の管理外です。鍵ファイルなども `config/` の下に置けます。設定の例は `docs/` にあります。
- 場所を変えたいときは、`--config`（または環境変数 `FHASHES_RECORD_CONFIG` / `FHASHES_REVIEW_CONFIG`）で設定ファイルを、設定の `state_dir` / `cache_dir` で状態とキャッシュの場所を指定します。相対パスは、設定ファイルのあるディレクトリが基準です。

## 記録する側（監視対象）

### 導入

監視に使うユーザー（例: `fhashes`）で行います。一般ユーザーで動かす場合、そのユーザーが読めるファイルだけが記録されます。読めないもの（存在するが中身を読めないファイル・ディレクトリ）は「読み取りエラー」として記録され、調べるときに報告されます。

```
git clone <このリポジトリ> ~/fhashes
cd ~/fhashes
cp docs/record.sample.yaml config/record.yaml
vi config/record.yaml             # host、include / exclude、upload を書く

bin/fhashes record                # 1 回実行して、スナップショットがストレージに届くことを確認する
```

### 設定（config/record.yaml）

| 項目 | 既定値 | 説明 |
|---|---|---|
| `host` | （必須） | スナップショットに書くホスト名。ホストごとに違う名前にする。英数字・`.`・`_`・`-` |
| `state_dir` | `../data/record` | 状態ファイルと送信待ちのスナップショットの置き場所 |
| `include` | （必須） | 監視するファイルのワイルドカード（下の規則を参照） |
| `exclude` | なし | 除外するもののワイルドカード。除外にマッチしたディレクトリの中には入らない |
| `reread_cycle` | `24` | この回数の実行で、すべてのファイルを一度は中身から読み直す |
| `upload.remote` | なし | 送り先（例: `fhashes-gcs:fhashes-snapshots/web1`）。スナップショットはこの直下に置く。書かなければ送らない |
| `upload.rclone_config` | なし（rclone の既定の場所） | rclone の設定ファイル（例: `rclone.conf`。相対パスは設定ファイルのある場所が基準） |
| `upload.rclone_options` | なし | rclone に渡す追加のオプション（ふつうは不要） |
| `upload.rclone` | `rclone` | rclone のコマンドのパス |

ワイルドカードの規則:

| 書き方 | 意味 |
|---|---|
| `*` | `/` 以外の 0 文字以上 |
| `?` | `/` 以外の 1 文字 |
| `[abc]` / `[!abc]` | 文字クラス / その否定 |
| `**` | 0 個以上のディレクトリ（`/**/` や末尾の `/**` のように単独で書く） |

- パスは絶対パスで書きます。ディレクトリの中身を全部監視するときは `/var/www/app/**` のように書きます。
- マウントポイント（別のファイルシステム）にも入ります。include を広く書く場合は、`/proc/**`・`/sys/**`・`/dev/**` やネットワーク上のディスクなど、入りたくないものを exclude に書いてください。
- シンボリックリンクはたどらず、リンク自体（リンク先のパス）を記録します。ただし、パターンの起点（`/var/www/app/current/**` の `current`）がディレクトリへのリンクなら、たどって中を記録します。途中のリンク（`uploads -> /data/uploads` など）の中を監視したい場合は、リンク先を include に書いてください。
- 起点のディレクトリ（`/var/www/app/**` の `/var/www/app`）が存在しない場合は、その回の記録全体が失敗します（設定の間違いやマウント外れのまま記録を続けないため）。
- アップロード用のディレクトリは丸ごと除外せず、`**/*.php` などは監視することを勧めます（Web シェルが置かれやすい場所です）。

### 定期実行（systemd）

毎時の実行は systemd のタイマーで行います。

- **システムのタイマーとして登録する場合**（管理者の作業）: `docs/systemd/fhashes-record.service` の `User=` と `ExecStart=` を、実際のユーザーと clone した場所に合わせてから、次を実行します。
  ```
  sudo cp docs/systemd/fhashes-record.service docs/systemd/fhashes-record.timer /etc/systemd/system/
  sudo systemctl daemon-reload
  sudo systemctl enable --now fhashes-record.timer
  ```
  一般ユーザーのまま、すべてのファイルを読めるようにしたい場合は、service ファイルの `AmbientCapabilities=CAP_DAC_READ_SEARCH` を有効にします。root で動かす場合は `User=` の行を消します。
- **ユーザーのタイマーとして登録する場合**（管理者権限なし）: service ファイルから `User=` の行を消して `~/.config/systemd/user/` に置き、`systemctl --user enable --now fhashes-record.timer` を実行します。ログアウト中も動かすには `loginctl enable-linger <ユーザー>` が必要です（環境によっては管理者の作業になります）。

その他:
- 実行頻度はタイマーの `OnCalendar=hourly` で変えます。実行時刻は、ホストごとに決まった 0〜5 分だけずらします（`FixedRandomDelay=true` は systemd 247 以降）。
- 負荷は `Nice=19` と `IOSchedulingClass=idle` で抑えます（後者はディスクのスケジューラーが BFQ の場合だけ効きます）。
- service ファイルには、書き込みを `data/` だけに制限する保護の設定をコメントで入れてあります。
- ログは `journalctl -u fhashes-record`（ユーザーのタイマーなら `journalctl --user -u fhashes-record`）で見ます。
- 手動で `bin/fhashes record` を実行しても構いません。ほかの実行と重なった場合、後から始めた方は何もせずに終わります。
- `bin/fhashes record --no-upload` は、スナップショットを作るだけで送りません。
- 送れなかったスナップショットは `data/record/outbox/` に残り、次の実行で一緒に送られます。3 時間以上送れないままだと、ログに警告が出ます。
- `record` の終了コードは、記録に失敗したか、送れなかったスナップショットがあれば 1、なければ 0 です。記録に失敗した回も、前に送れなかったスナップショットの送信は行います。

### 運用上の注意

- **`git clean -fdx` は使わないでください。** `data/record/outbox/` の送れていないスナップショットが消えます。更新は `git pull` で行います（clone し直すと、設定と状態が消えます）。
- **Web サーバーのユーザーが書き込める場所（`/var/www` の下など）に clone しないでください。** 状態と送信待ちのスナップショットを書き換えられるおそれがあります。
- 状態ファイル（`data/record/state.sqlite3`）が壊れた場合は、自動で `state.sqlite3.broken-<日時>` として残し、作り直して記録を続けます。このとき、ハッシュチェーンは「状態ファイルが失われた」と記録されます。
- すべてのファイルを今すぐ読み直したいときは、状態ファイルを消してから実行します（`rm data/record/state.sqlite3* && bin/fhashes record`）。このとき、ハッシュチェーンは「状態ファイルが失われた」と記録され、調べるときに報告されます。

## ストレージ

ストレージ側の設定は、運用で行います（fhashes は関与しません）。どのクラウドでも、やることは次の 4 つです。

1. 入れ物（バケット / コンテナ）を作る
2. **消せなくする**設定（保持期間。例: 180 日）。**ロックすると取り消せない**ので、最初はロックせずに試す
3. **期限後に消す**設定（ライフサイクル。保持期間より少し長く）
4. 鍵を 2 種類用意する（どちらもバケット単位の権限でよい）
   - 記録する側（監視対象）用: **作成と読み取りだけ**できる鍵（上書き・削除はできない。読み取りは、送信済みのものを送り直したときに確かめるため）
   - 調べる側用: **読み取りと一覧だけ**できる鍵

| | 消せなくする | 期限後に消す | 記録する側に渡す権限 | 調べる側に渡す権限 | 手順 |
|---|---|---|---|---|---|
| AWS S3 | オブジェクトロック | ライフサイクル | `s3:PutObject`、`s3:GetObject` | `s3:ListBucket`、`s3:GetObject` | [docs/storage-aws-s3.md](docs/storage-aws-s3.md) |
| GCS | 保持ポリシー | ライフサイクル | `roles/storage.objectCreator`、`roles/storage.objectViewer` | `roles/storage.objectViewer` | [docs/storage-gcp-gcs.md](docs/storage-gcp-gcs.md) |
| Azure Blob | 不変ストレージ（時間ベースの保持） | ライフサイクル管理 | SAS（`rcw`） | SAS（`rl`） | [docs/storage-azure-blob.md](docs/storage-azure-blob.md) |

- スナップショットは、`upload.remote` の直下に `web1-20260924T010000Z-00000123.ndjson.gz` のような名前で置きます。ホストごとに場所を分ける（`fhashes-snapshots/web1` など）ことを勧めます（調べるときの一覧が小さく済みます）。
- 送信に必要な rclone のオプションは、fhashes が付けます。設定するのは `upload.remote` と `upload.rclone_config` だけです。
- 記録する側の鍵では、同じバケットのほかのホストのスナップショット（ファイル一覧とハッシュ）を読めます。避けたい場合は、ホストごとにバケットを分けるか、権限を場所で絞ります（各手順の「より安全にする場合」）。
- 容量の目安: 10 万ファイルでスナップショット 1 つが約 5MB。毎時・180 日で、10 万ファイルあたり約 20GB です。

## 調べる側

### 導入

```
git clone <このリポジトリ> fhashes
cd fhashes
cp docs/review.sample.yaml config/review.yaml
vi config/review.yaml             # hosts に、調べるホストとストレージ（読み取り専用の鍵）を書く
```

### 設定（config/review.yaml）

| 項目 | 既定値 | 説明 |
|---|---|---|
| `hosts` | （必須） | 調べるホストと、そのスナップショットを置いているストレージ（rclone の場所）。`ホスト名: 場所` の形で書く。場所は記録する側の `upload.remote` と同じところ（鍵は読み取り専用のもの） |
| `cache_dir` | `../data/cache` | ダウンロードしたスナップショットのキャッシュ |
| `rclone_config` | なし（rclone の既定の場所） | rclone の設定ファイル（相対パスは設定ファイルのある場所が基準） |
| `rclone_options` | なし | rclone に渡す追加のオプション（ふつうは不要） |
| `rclone` | `rclone` | rclone のコマンドのパス |

### review: 期間を指定して調べる

```
bin/fhashes review web1 --from '2026-09-20 10:00' --to '2026-09-22 15:00'
bin/fhashes review web1 --from 2026-09-20 --to 2026-09-22 --path '*.php'
bin/fhashes review web1 --from 2026-09-20 --to 2026-09-22 --type added,modified --format csv
bin/fhashes review web1 --path '*/uploads/*/shell.php'   # 全期間。このファイルがいつ現れ、いつ変わったか
```

出力の例:

```
ホスト  : web1
調査期間: 2026-09-20 10:00:00 〜 2026-09-22 15:00:00
時刻の表示: JST（+09:00）（実行環境のタイムゾーン。TZ で変えられる）
変化の条件: 変更された可能性のある期間が、調査期間と重なるもの

[監視の状況]
✓ 期間の直前のスナップショット: 2026-09-20 09:02:00（seq 22）
✓ 期間の直後のスナップショット: 2026-09-22 15:02:00（seq 73）
! 記録の間隔の乱れ: 2026-09-21 11:02:00 〜 2026-09-21 15:02:00（4.0 時間。普段は約 60 分）。この間の変更は、前後の記録の間のどこかとしか分かりません
✓ ハッシュチェーン: 正常
✓ 不正なスナップショット: なし
✓ 監視範囲の変更: なし
✓ 読み取りエラー: なし

[変化]
この時点では元の状態  この時点では新しい状態  種別      パス
--------------------  ----------------------  --------  -------------------------------------------------
2026-09-21 03:02:00   2026-09-21 04:02:41     modified  /var/www/app/.htaccess
2026-09-21 03:02:00   2026-09-21 04:02:41     added     /var/www/app/wp-content/uploads/2026/09/cache.php
2026-09-22 14:02:00   2026-09-22 15:02:39     modified  /var/www/app/wp-includes/version.php

3 件（変更されたのは、左 2 列の時刻の間のどこか）

[判定] 監視の状況に問題はありません。上の変化がすべて説明できれば、監視範囲のファイル内容について、この期間に説明のつかない変更はありません。
```

- **変化**: 前後のスナップショットを比べて見つけた追加（added）・変更（modified）・削除（deleted）です。変更されたのは、「この時点では元の状態」と「この時点では新しい状態」の間のどこかです。
- **監視の状況**: 変化の一覧を信用してよいかどうかの確認です。ハッシュチェーンの異常（記録の書き換えや欠落の疑い）、不正なスナップショット、監視範囲の変更、読み取りエラーを確かめます。読み取りエラーのファイルは、消えたとはみなさず、読めるようになったときにエラーになる前の状態と比べます。
- **記録の間隔**: 実際の記録から普段の間隔を推定し、その 1.5 倍より空いたところを `!` で報告します。その間の変更も前後の記録を比べれば見つかるので、問題とはみなしません（判定と終了コードに影響しません）。
- **判定**: 監視の状況に問題がなく、変化がすべて説明できれば、「監視範囲のファイル内容について、この期間に説明のつかない変更はない」と言えます。
- `--from` / `--to` は省けます。`--from` を省くと最初のスナップショットから、`--to` を省くと最新のスナップショットまでを調べます。日付だけを書いた場合、`--to` はその日の終わりまでを含みます。
- 全期間を調べると、ダウンロードの量が多くなります（10 万ファイル・180 日分で約 20GB）。始める前に量を出すので、多すぎれば Ctrl-C で止めて期間を指定してください。
- 表示と `--from` / `--to` の解釈には、実行環境のタイムゾーン（`TZ`）を使います（`TZ=UTC bin/fhashes review …` で変えられます）。`--from 2026-09-20T01:00Z` のように、タイムゾーンを書いて指定することもできます。
- 変化の期間の判定は、既定では「変更された可能性のある期間が、指定期間と重なるもの」です（取りこぼしがありません）。`--detected` を付けると「指定期間に検知したもの」になります。
- `--path`（ワイルドカード。複数指定するといずれかに一致するもの。`/` で始まらなければどのディレクトリの下でもよい）と `--type` で、変化を絞り込めます。
- `--format csv` / `json` では、変化だけを出します。時刻は UTC（`2026-09-21T18:02:41Z` の形。秒まで）です。監視の状況に問題があれば、標準エラー出力に書きます。
- 終了コードは、監視の状況に問題があれば 1、なければ 0 です。
- 1 台ずつ調べます。複数のホストを調べるときは、ホストごとに実行してください（例: `for h in web1 web2; do bin/fhashes review $h --from … --to …; done`）。

### status: 全ホストの状況を見る

```
bin/fhashes status
```

```
ホスト  最新のスナップショット  経過      ファイル数  エラー    直近 24 時間の数  状況
------  ----------------------  --------  ----------  --------  ----------------  ----------------------------
db1     2026-09-26 15:00:00     37 分     1200        3         21                読み取りエラーあり、（参考）直近 24 時間に間隔の乱れあり
web1    2026-09-26 15:00:00     37 分     48213       0         24                OK
web2    2026-09-26 10:00:00     5.6 時間  180512      0         19                （参考）最新のスナップショットが普段の間隔より古い
```

- 設定の `hosts` に書いたホストをすべて表示します。
- スナップショットが 1 つもない・最新のスナップショットが不正・ハッシュチェーンに異常がある・読み取りエラーがある場合は、「状況」に表示します。1 台でも当てはまるホストがあると、終了コードは 1 です。
- 最新のスナップショットが普段の間隔の 1.5 倍より古い場合と、直近 24 時間に間隔の乱れがある場合は、「（参考）」として表示します。終了コードには影響しません。

### ダウンロードとキャッシュ

- `review` は、指定した期間を調べるのに必要なスナップショットだけをダウンロードします。
- ダウンロードしたスナップショットは `data/cache/` にキャッシュし、次からはそれを使います。消すときは `bin/fhashes clean` です。
- 量の目安: 10 万ファイルのホストの 1 日分（24 個）で約 120MB です。

## できないこと

- パーミッション・所有者の変化は記録しません。
- 記録と記録の間に「変更して元に戻す」操作をされると、分かりません。
- 変更された時刻は、実行間隔（既定 1 時間）の幅でしか分かりません。また、時刻は監視対象の時計によるもので、時計が正しいかどうかは確かめません（NTP などで合わせておいてください）。
- 監視対象の root を取られると、それ以降の記録は信用できません（記録を止める、偽の記録を送る、など）。ただし、それまでにストレージへ送った記録は消せません。記録が止まれば、記録の間隔の乱れとして報告されます。
- 読み直しの順番が来るまでは、ctime などが変わらないファイルの中身は読みません。ctime までごまかされた変更は、最大で `reread_cycle` 回後の読み直しまで分かりません。

## テスト

```
python3 -m unittest discover -s tests
```

テスト用のファイルは一時ディレクトリ（`/tmp/fhashes-test` など。環境変数 `FHASHES_TEST_DIR` で変更可）の下に作られ、終了時に消えます。rclone が見つからない場合、rclone を使うテストはスキップします（`FHASHES_TEST_RCLONE` で rclone の場所を指定できます）。

参考（開発環境での計測。1 つのディレクトリに 15 万個の空ファイル）: record は 1 回目約 9 秒、2 回目以降約 8 秒、メモリ約 70MB。review（スナップショット 3 つ）は約 5 秒、メモリ約 20MB（rclone を除く）。
