# fhashes

Web システムのサーバーのファイルのハッシュを定期的に記録し、侵入や改ざんが疑われるときに「いつ・何が変わったか」を後から調べるためのツールです。

> **試験段階です。** 設定や記録の形式は、予告なく変わることがあります。

例えば次のような問いに答えます。

- 脆弱性の公表からパッチ適用までの間に、意図しないファイルの変更はなかったか
- 見つかった不審なファイルは、いつ現れたか。同じ頃にほかに何が変わったか
- このファイルは、いつからこの内容か

## 仕組み

```
監視対象のサーバー（記録する側）
  定期的に fhashes record（間隔はサーバーごとに決める。例: 1 時間ごと、6 時間ごと）
    全ファイルのパスとハッシュの一覧（以下「記録」）を作り、rclone でストレージへ送る
        │
        ▼
ストレージ（S3 / GCS / Azure Blob など。書き換え・削除できない設定にする）
        │
        ▼
調べる側（どのマシンでもよい）
  fhashes log web1 [--from …] [--to …]
    必要な期間の記録を取ってきて、前後を比べて変化を表示する
```

- 記録するのは、ファイルの内容のハッシュ（SHA-256）です。ファイルの中身そのものは送りません。
- 中身を読んでハッシュを計算するのは、ctime・サイズ・inode が前回と変わったファイルと、毎回全体の約 1/`reread_cycle` だけです。`reread_cycle` 回の実行で、すべてのファイルが一度は読み直されます。
- ストレージを書き換え・削除できない設定（WORM）にしておけば、監視対象が乗っ取られても、それまでの記録は消せません。
- 調べる側は何も保存しません（ダウンロードした記録をキャッシュするだけです）。
- 通知はしません。必要になったときに記録をさかのぼって調べるためのツールです。

設計と、その理由は [DESIGN.md](DESIGN.md) にあります。

## 必要なもの

- Python 3.6 以上と PyYAML（`apt install python3-yaml` / `dnf install python3-pyyaml`）。pip は使いません。
- rclone **1.61 以降**（apt / dnf で入るものは古いことがあるので、[rclone.org](https://rclone.org/downloads/) の単体バイナリを勧めます）。送り先の設定（下の「ストレージ」）は事前に済ませておきます。rclone の設定ファイルは `config/rclone.conf` に置くことを勧めます。

## コマンド

| コマンド | 使う場所 | 説明 |
|---|---|---|
| `bin/fhashes record` | 記録する側 | ファイルを調べて記録を作り、送信待ちのものと一緒にストレージへ送る |
| `bin/fhashes log <host> [--from …] [--to …]` | 調べる側 | 1 台のホストについて、期間内の変化の履歴と監視の状況を表示する |
| `bin/fhashes diff <host> [--from …] [--to …]` | 調べる側 | 1 台のホストについて、期間の最初と最後の状態の差を場所の木で表示する |
| `bin/fhashes status` | 調べる側 | ホストごとの最新の記録、記録の間隔、記録の遅れ、異常を表示する |
| `bin/fhashes clean` | 調べる側 | ダウンロードした記録のキャッシュを消す |

v0.2 までの `review` は、v0.3 で `log` に改めました（使い方も、`--type` の書き方を印にそろえるなど変わっています）。

`-v` を付けると詳しいログを出します。どのコマンドも `--config` で設定ファイルを指定できます。

## ファイルの置き場所

設定・状態・キャッシュは、既定ではすべて clone したディレクトリの中に置きます（`/etc` やホームディレクトリには置きません）。

```
<clone したディレクトリ>/
  config/record.yaml     記録する側の設定（docs/record.sample.yaml をコピーして書く）
  config/review.yaml     調べる側の設定（docs/review.sample.yaml をコピーして書く）
  data/record/           記録する側の状態（state.sqlite3、送信待ちの outbox/ など）
  data/cache/            調べる側がダウンロードした記録のキャッシュ
```

- `config/` の下と `data/` は git の管理外です。鍵ファイルなども `config/` の下に置けます。設定の例は `docs/` にあります。
- 場所を変えたいときは、`--config`（または環境変数 `FHASHES_RECORD_CONFIG` / `FHASHES_REVIEW_CONFIG`）で設定ファイルを、設定の `state_dir` / `cache_dir` で状態とキャッシュの場所を指定します。相対パスは、設定ファイルのあるディレクトリが基準です。

## 記録する側（監視対象）

### 導入

監視に使うユーザー（例: `fhashes`）で行います。一般ユーザーで動かす場合、そのユーザーが読めるファイルだけが記録されます。読めないもの（存在するが中身を読めないファイル・ディレクトリ）は「読み取りエラー」として記録され、調べるときに報告されます。

```
git clone <このリポジトリ> ~/fhashes
cd ~/fhashes
cp docs/record.sample.yaml config/record.yaml
vi config/record.yaml             # host、include / exclude、upload を書く

bin/fhashes record                # 1 回実行して、記録がストレージに届くことを確認する
```

### 設定（config/record.yaml）

| 項目 | 既定値 | 説明 |
|---|---|---|
| `host` | （必須） | 記録に書くホスト名。ホストごとに違う名前にする。英数字・`.`・`_`・`-` |
| `state_dir` | `../data/record` | 状態ファイルと送信待ちの記録の置き場所 |
| `include` | （必須） | 監視するファイルのワイルドカード（下の規則を参照） |
| `exclude` | なし | 除外するもののワイルドカード。除外にマッチしたディレクトリの中には入らない |
| `reread_cycle` | `24` | この回数の実行で、すべてのファイルを一度は中身から読み直す（下の「実行間隔と読み直しの周期」） |
| `upload.remote` | なし | 送り先（例: `fhashes-gcs:fhashes-snapshots/web1`）。記録はこの直下に置く。書かなければ送らない |
| `upload.rclone_config` | なし（rclone の既定の場所） | rclone の設定ファイル（例: `rclone.conf`。相対パスは設定ファイルのある場所が基準） |
| `upload.rclone_options` | なし | rclone に渡す追加のオプション（ふつうは不要） |
| `upload.rclone` | `rclone` | rclone のコマンドのパス |

ワイルドカードの規則:

| 書き方 | 意味 |
|---|---|
| `*` | `/` 以外の 0 文字以上 |
| `?` | `/` 以外の 1 文字 |
| `[abc]` / `[!abc]` | 文字クラス / その否定 |
| `**` | 0 個以上のディレクトリ（`/**/` や末尾の `/**` のように単独で書く） |

- パスは絶対パスで書きます。ディレクトリの中身を全部監視するときは `/var/www/app/**` のように書きます。
- マウントポイント（別のファイルシステム）にも入ります。include を広く書く場合は、`/proc/**`・`/sys/**`・`/dev/**` やネットワーク上のディスクなど、入りたくないものを exclude に書いてください。
- シンボリックリンクはたどらず、リンク自体（リンク先のパス）を記録します。ただし、パターンの起点（`/var/www/app/current/**` の `current`）がディレクトリへのリンクなら、たどって中を記録します。途中のリンク（`uploads -> /data/uploads` など）の中を監視したい場合は、リンク先を include に書いてください。
- 起点のディレクトリ（`/var/www/app/**` の `/var/www/app`）が存在しない場合は、その回の記録全体が失敗します（設定の間違いやマウント外れのまま記録を続けないため）。
- アップロード用のディレクトリは丸ごと除外せず、`**/*.php` などは監視することを勧めます（Web シェルが置かれやすい場所です）。

### 実行間隔と読み直しの周期

どちらも、サーバーに合わせて決めます。同梱のタイマーの 1 時間ごとと、`reread_cycle` の既定値 24 は、例であって勧める値ではありません。

- **実行間隔**（タイマーで決める）: 「いつ変わったか」は、この間隔の幅でしか分かりません。短いほど時期を狭められますが、走査の負荷がその回数だけかかります。更新の少ないサーバーや、ディスクが遅い（HDD の）サーバーは、4 時間ごと・6 時間ごとなどにします。ホストごとに違ってかまいません（調べる側は設定を持たず、実際の記録から間隔を求めます）。
- **読み直しの周期**（`reread_cycle`）: ctime などが変わらないファイルも、`reread_cycle` 回の実行に 1 回は中身から読み直します（ctime をごまかした変更への保険）。一巡にかかる時間は「実行間隔 × `reread_cycle`」です（1 時間ごと・24 なら 1 日、6 時間ごと・4 なら 1 日、6 時間ごと・28 なら 7 日）。小さいほど早く気づけますが、毎回読む量（全体の 1/`reread_cycle`）が増えます。実行間隔を変えたら、一巡の時間が望む長さになるように見直してください。

### 定期実行（systemd）

定期実行は systemd のタイマーで行います。同梱のタイマー（`docs/systemd/fhashes-record.timer`）は 1 時間ごと（`OnCalendar=hourly`）なので、必要なら変えてから登録します（下の「その他」）。

- **システムのタイマーとして登録する場合**（管理者の作業）: `docs/systemd/fhashes-record.service` の `User=` と `ExecStart=` を、実際のユーザーと clone した場所に合わせてから、次を実行します。
  ```
  sudo cp docs/systemd/fhashes-record.service docs/systemd/fhashes-record.timer /etc/systemd/system/
  sudo systemctl daemon-reload
  sudo systemctl enable --now fhashes-record.timer
  ```
  一般ユーザーのまま、すべてのファイルを読めるようにしたい場合は、service ファイルの `AmbientCapabilities=CAP_DAC_READ_SEARCH` を有効にします。root で動かす場合は `User=` の行を消します。
- **ユーザーのタイマーとして登録する場合**（管理者権限なし）: service ファイルから `User=` の行を消して `~/.config/systemd/user/` に置き、`systemctl --user enable --now fhashes-record.timer` を実行します。ログアウト中も動かすには `loginctl enable-linger <ユーザー>` が必要です（環境によっては管理者の作業になります）。

その他:
- 実行間隔はタイマーの `OnCalendar=` で変えます。例: 1 時間ごと `hourly`、4 時間ごと `*-*-* 00/4:00:00`、6 時間ごと `*-*-* 00/6:00:00`。変えたら `systemctl daemon-reload` を実行します。
- 負荷は `Nice=19` と `IOSchedulingClass=idle` で抑えます（後者はディスクのスケジューラーが BFQ の場合だけ効きます）。
- service ファイルには、書き込みを `data/` だけに制限する保護の設定をコメントで入れてあります。
- ログは `journalctl -u fhashes-record`（ユーザーのタイマーなら `journalctl --user -u fhashes-record`）で見ます。
- 手動で `bin/fhashes record` を実行しても構いません。ほかの実行と重なった場合、後から始めた方は何もせずに終わります。
- `bin/fhashes record --no-upload` は、記録を作るだけで送りません。
- 送れなかった記録は `data/record/outbox/` に残り、次の実行で一緒に送られます。3 時間以上送れないままだと、ログに警告が出ます。
- `record` の終了コードは、記録に失敗したか、送れなかった記録があれば 1、なければ 0 です。記録に失敗した回も、前に送れなかった記録の送信は行います。

### 運用上の注意

- **`git clean -fdx` は使わないでください。** `data/record/outbox/` の送れていない記録が消えます。更新は `git pull` で行います（clone し直すと、設定と状態が消えます）。
- **Web サーバーのユーザーが書き込める場所（`/var/www` の下など）に clone しないでください。** 状態と送信待ちの記録を書き換えられるおそれがあります。
- 状態ファイル（`data/record/state.sqlite3`）が壊れた場合は、自動で `state.sqlite3.broken-<日時>` として残し、作り直して記録を続けます。このとき、ハッシュチェーンは「状態ファイルが失われた」と記録されます。
- すべてのファイルを今すぐ読み直したいときは、状態ファイルを消してから実行します（`rm data/record/state.sqlite3* && bin/fhashes record`）。このとき、ハッシュチェーンは「状態ファイルが失われた」と記録され、調べるときに報告されます。

## ストレージ

ストレージ側の設定は、運用で行います（fhashes は関与しません）。どのクラウドでも、やることは次の 4 つです。

1. 入れ物（バケット / コンテナ）を作る
2. **消せなくする**設定（保持期間。例: 180 日）。**ロックすると取り消せない**ので、最初はロックせずに試す
3. **期限後に消す**設定（ライフサイクル。保持期間より少し長く）
4. 鍵を 2 種類用意する（どちらもバケット単位の権限でよい）
   - 記録する側（監視対象）用: **作成と読み取りだけ**できる鍵（上書き・削除はできない。読み取りは、送信済みのものを送り直したときに確かめるため）
   - 調べる側用: **読み取りと一覧だけ**できる鍵

| | 消せなくする | 期限後に消す | 記録する側に渡す権限 | 調べる側に渡す権限 | 手順 |
|---|---|---|---|---|---|
| AWS S3 | オブジェクトロック | ライフサイクル | `s3:PutObject`、`s3:GetObject` | `s3:ListBucket`、`s3:GetObject` | [docs/storage-aws-s3.md](docs/storage-aws-s3.md) |
| GCS | 保持ポリシー | ライフサイクル | `roles/storage.objectCreator`、`roles/storage.objectViewer` | `roles/storage.objectViewer` | [docs/storage-gcp-gcs.md](docs/storage-gcp-gcs.md) |
| Azure Blob | 不変ストレージ（時間ベースの保持） | ライフサイクル管理 | SAS（`rcw`） | SAS（`rl`） | [docs/storage-azure-blob.md](docs/storage-azure-blob.md) |

- 記録は、`upload.remote` の直下に `web1-20260924T010000Z-00000123.ndjson.gz` のような名前で置きます。ホストごとに場所を分ける（`fhashes-snapshots/web1` など）ことを勧めます（調べるときの一覧が小さく済みます）。
- 送信に必要な rclone のオプションは、fhashes が付けます。設定するのは `upload.remote` と `upload.rclone_config` だけです。
- 記録する側の鍵では、同じバケットのほかのホストの記録（ファイル一覧とハッシュ）を読めます。避けたい場合は、ホストごとにバケットを分けるか、権限を場所で絞ります（各手順の「より安全にする場合」）。
- 容量の目安: 10 万ファイルで記録 1 件が約 5MB。180 日で、10 万ファイルあたり 1 時間ごとなら約 20GB、6 時間ごとなら約 3.6GB です。

## 調べる側

### 導入

```
git clone <このリポジトリ> fhashes
cd fhashes
cp docs/review.sample.yaml config/review.yaml
vi config/review.yaml             # hosts に、調べるホストとストレージ（読み取り専用の鍵）を書く
```

### 設定（config/review.yaml）

| 項目 | 既定値 | 説明 |
|---|---|---|
| `hosts` | （必須） | 調べるホストと、その記録を置いているストレージ（rclone の場所）。`ホスト名: 場所` の形で書く。場所は記録する側の `upload.remote` と同じところ（鍵は読み取り専用のもの） |
| `cache_dir` | `../data/cache` | ダウンロードした記録のキャッシュ |
| `rclone_config` | なし（rclone の既定の場所） | rclone の設定ファイル（相対パスは設定ファイルのある場所が基準） |
| `rclone_options` | なし | rclone に渡す追加のオプション（ふつうは不要） |
| `rclone` | `rclone` | rclone のコマンドのパス |

### log: 期間の変化の履歴を見る

```
bin/fhashes log web1 --from '2026-09-20 10:00' --to '2026-09-22 15:00'
bin/fhashes log web1 --from 4d                         # 4 日前から今まで
bin/fhashes log web1 --from 2026-09-20 --to 2026-09-22 --path '*.php'
bin/fhashes log web1 --from 2026-09-20 --to 2026-09-22 --type AM --format csv
bin/fhashes log web1 --path '*/uploads/*/shell.php'    # 全期間。このファイルがいつ現れ、いつ変わったか
```

出力の例:

```

調査期間: 2026-09-20 10:00 - 2026-09-22 15:00

[変化の履歴]
2026-09-21 03:02 - 04:02
/var/www/app/
    M .htaccess
    A wp-content/uploads/2026/09/cache.php

2026-09-22 14:02 - 15:02
/var/www/app/
    M index.php
    wp-includes/
        M js/jquery/jquery.js
        M version.php

A  追加      1    D  削除  0    M  変更  4    T  種別変更  0
?  状態不明  0

[監視の状況]
期間の直前の記録: 2026-09-20 09:02
期間の直後の記録: 2026-09-22 15:02
記録の件数: 50
記録の間隔: 中央値 60 分、最大値 4.0 時間（2026-09-21 11:02 - 15:02）
記録の欠落: なし
記録の不一致: なし
記録のやり直し: なし
不正な記録: なし
監視範囲の変更: なし
読み取りエラー: なし
```

- **変化の履歴**: 前後の記録を比べて見つけた変化を、時期ごとに場所の木で出します（古い順。`git log --name-status` に当たります）。変化したのは、時期の範囲のどこかです（前の記録の開始 - その記録の終了）。時期のまとまりの後には空行を入れます。
  - 印は `A` 追加、`D` 削除、`M` 変更、`T` 種別変更（通常のファイル ⇔ シンボリックリンク）、`?` 状態不明（読み取りエラーで中身が分からない）です。
  - 木は diff と同じく、監視範囲の起点（`include` のディレクトリ）を根にし、子が 1 つしかないディレクトリは 1 行につなげます。
  - 読み取りエラーの間に変わったものは、時期の始まりが早くなります（読めなくなる前の状態と比べるため）。こうしたものは、別の時期のまとまりとして出ます。
  - 最後の表は、印ごとの件数です（凡例を兼ねます）。
- **監視の状況**: 変化の履歴を信用してよいかどうかの確認です。

  | 項目 | 意味 |
  |---|---|
  | 期間の直前の記録 / 直後の記録 | 期間の始まりと終わりの状態を知るための記録。`なし` なら、期間の端の変化が分からない（`--from` / `--to` を省いたときは、最初と最新の記録を出す） |
  | 記録の件数、記録の間隔 | 期間の中に始まった記録の数と、間隔の中央値・最大値（とその場所）。間隔は期間の直前・直後の記録も含めて求める。最大値のところは、変化の時期を狭められない |
  | 記録の欠落 | 届いていない（または消された）記録の数と、その場所 |
  | 記録の不一致 | 直前の記録と一致しない記録。書き換え・すり替えの疑い |
  | 記録のやり直し | 監視対象の状態ファイルが失われ、記録が最初からやり直された |
  | 不正な記録 | 形式が壊れている記録（途中で切れている、など） |
  | 監視範囲の変更 | include / exclude が変わった記録。範囲に出入りしたファイルは、変化として数えない |
  | 読み取りエラー | 読めないファイルがあった記録の数と、1 件あたりの最大のファイル数。読めない間は変化を見逃しうる（読めるようになったときに、読めなくなる前の状態と比べる）。期間の終わりでも読めないままのものは、「期間の終わりでもエラーのまま」として数を出す |

- 終了コードは、次のどれかがあれば 1、なければ 0 です: 期間の直前・直後の記録がない、記録の欠落・不一致・やり直し、不正な記録、読み取りエラー。記録の間隔と監視範囲の変更は、終了コードに影響しません。
- 終了コードが 0 で、変化の履歴がすべて説明できれば、「監視範囲のファイル内容について、この期間に説明のつかない変更はない」と言えます。
- `--from` / `--to` は省けます。`--from` を省くと最初の記録から、`--to` を省くと最新の記録までを調べます。日付だけを書いた場合、`--to` はその日の終わりまでを含みます。
- `--from` / `--to` には、今からどれだけ前かも書けます。`4d`（4 日前）、`12h`（12 時間前）、`30m`（30 分前）、`2w`（2 週間前）です。`4d` はちょうど 96 時間前で、暦の日の 0 時ではありません（日の始めからにしたいときは、日付で書きます）。マイナスは付けません（`--from 4d`）。
- 全期間を調べると、ダウンロードの量が多くなります（10 万ファイル・180 日分で約 20GB）。端末で実行すると、進み具合（全体の量を含む）を 1 行で出し、終わったら消します。多すぎれば Ctrl-C で止めて期間を指定してください。パイプや cron など、端末でないときは何も出しません。
- 表示と `--from` / `--to` の解釈には、実行環境のタイムゾーン（`TZ`）を使います（`TZ=UTC bin/fhashes log …` で変えられます）。`--from 2026-09-20T01:00Z` のように、タイムゾーンを書いて指定することもできます。
- 既定では、変化の時期が調査期間と重なるものを出します（取りこぼしがありません）。`--detected` を付けると「指定期間に検知したもの」になります。
- 絞り込み: `--path` / `--type` は「これだけ」、`--not-path` / `--not-type` は「これを除く」です（diff と同じ）。`--path` はワイルドカードで、`/` で始まらなければどのディレクトリの下でもよいものとします。`--type` には印をつなげて書きます（`A`、`AM`）。どれも何度でも指定でき、両方あれば絞ってから除きます。
- `--format csv` / `json` では、変化だけを 1 行 1 件で出します。時刻は UTC（`2026-09-21T18:02:41Z` の形。秒まで）です。`type` の列は `added` / `modified` / `deleted` です。監視の状況に問題があれば、標準エラー出力に書きます。
- 1 台ずつ調べます。複数のホストを調べるときは、ホストごとに実行してください（例: `for h in web1 web2; do bin/fhashes log $h --from … --to …; done`）。

### diff: 期間の最初と最後の差を見る

```
bin/fhashes diff web1 --from 2026-09-20 --to 2026-09-23
bin/fhashes diff web1 --from 2026-09-20 --path '/var/www/app/wp-content/**'
bin/fhashes diff web1 --from 2026-09-20 --type A      # 追加だけ（AM で追加と変更）
bin/fhashes diff web1 --from 4d --not-type D --not-path '*/cache/**'   # 削除とキャッシュを除く
```

log が「いつ何が変わったか」を時刻の順に出すのに対し、diff は「期間の最初と最後で何が違うか」を、場所の木で 1 ファイル 1 行に出します（`git diff A B` に当たります）。システムの構造を知っている人が眺めて、見慣れない名前のファイルや、変わるはずのない場所（何年も前の uploads のディレクトリなど）の変化に気づくためのものです。

```
[差分]
/var/www/app/
    M .htaccess                    2026-09-21 03:02 - 04:02
    M index.php                    2026-09-20 09:02 - 2026-09-22 15:02（2 回）
    = wp-config.php                2026-09-21 03:02 - 2026-09-23 03:02（2 回）
    wp-content/
        plugins/aaa-plugin/        2026-09-20 09:02 - 10:02
            M data/config.php
            M js/main.js
            M view/form.php
        uploads/
            A 2024/05/cache.php    2026-09-21 03:02 - 04:02
            ~ 2026/09/x.php        2026-09-21 03:02 - 2026-09-23 03:02（2 回）
    wp-includes/                   2026-09-22 14:02 - 15:02
        A blocks/new-block.php
        css/
            A new.css
            D old.css
        M js/jquery/jquery.js
        M version.php

A  追加        3    D  削除        1    M  変更      7    T  種別変更  0
=  変化後復元  1    ~  追加後削除  1    ?  状態不明  0
```

- 印は、期間の最初と最後の状態を比べた結果です。`A` `D` `M` `T` は git と同じ意味です。`=` は最初と最後が同じだが途中で変化があったもの、`~` は期間中に置かれて消されたもの、`?` は読み取りエラーで最初か最後の状態が分からないものです。記号の印は「普通の追加・変更・削除ではない」ことを表すだけで、怪しいかどうかは見る人が判断します。
- 時期は、そのファイルの最初の変化の始まりから最後の変化の終わりまでです（変化したのはこの範囲のどこか）。何度も変わったものには回数を添えます。1 回ずつの時期は log で見ます。
- 木は、監視範囲の起点（`include` に書いたディレクトリ。例: `/var/www/app/**` なら `/var/www/app/`）ごとに分け、起点のディレクトリを根にします。変化の量にかかわらず、いつも同じ位置から読めます。1 つのファイルを指す `include`（`/etc/passwd` など）は、フルパスの 1 行です。
- 子が 1 つしかないディレクトリは 1 行につなげます。ディレクトリの下がすべて同じ時期なら、時期はディレクトリの行に 1 回だけ書きます。
- 最後の表は、印ごとの件数です（凡例を兼ねます）。1 段目が git と同じ普通の変化、2 段目が普通でない変化です。
- 絞り込み: `--path` / `--type` は「これだけ」、`--not-path` / `--not-type` は「これを除く」です。どれも何度でも指定でき、両方あれば絞ってから除きます。`--type` / `--not-type` には印をつなげて書きます（`A`、`AM`、`'=~?'`。記号の印は、シェルが解釈しないように引用符で囲みます）。最後の件数の表は、表示したものの件数です。
- `--from` / `--to`（省けば最初・最新の記録）と `--path` / `--not-path` は log と同じです。[監視の状況] と終了コードも log と同じです。

### status: 全ホストの状況を見る

```
bin/fhashes status
```

```
ホスト  最新の記録        間隔の中央値  間隔の最大値  ファイル数  エラー  状況
------  ----------------  ------------  ------------  ----------  ------  ----------------------
db1     2026-09-26 15:00  60 分         60 分              1,200       3  読み取りエラー
web1    2026-09-26 15:00  60 分         60 分             48,213       0  OK
web2    2026-09-26 10:00  60 分         60 分            180,512       0  記録の遅れ（4.0 時間）
web3    -                 -             -                      -       -  記録なし
```

- 設定の `hosts` に書いたホストをすべて表示します。
- 「間隔の中央値」「間隔の最大値」は、直近 24 件の記録の間隔です。
- 「状況」には、次の問題を出します（重なれば「、」で並べます）。1 台でもあれば、終了コードは 1 です。
  - 記録なし
  - 記録の遅れ: 次の記録が届くはずの時刻（最新の記録の終了 + 間隔の中央値）を 5 分過ぎても届いていない。サーバーが止まっている、タイマーが動いていない、セットアップが壊れた、走査が遅くなった（ファイル数の急増、負荷）などが考えられます。かっこの中は、届くはずの時刻からの遅れです（上の web2 は 10:00 から記録がありません）。
  - 最新の記録が不正、直前の記録が不正（最新の記録のつながりを確かめられない）
  - 記録の欠落 / 不一致 / やり直し、読み取りエラー（最新の記録について）

### ダウンロードとキャッシュ

- `log` と `diff` は、指定した期間を調べるのに必要な記録だけをダウンロードします。
- ダウンロードした記録は `data/cache/` にキャッシュし、次からはそれを使います。記録を検証した結果も隣に残すので、同じ期間を繰り返し調べるときは速くなります（変化のない記録は展開しません）。消すときは `bin/fhashes clean` です。
- 量の目安: 10 万ファイルのホストで、記録 1 件あたり約 5MB です（1 時間ごとなら 1 日分 24 件で約 120MB）。

## できないこと

- パーミッション・所有者の変化は記録しません。
- 記録と記録の間に「変更して元に戻す」操作をされると、分かりません。
- 変更された時刻は、実行間隔の幅でしか分かりません。また、時刻は監視対象の時計によるもので、時計が正しいかどうかは確かめません（NTP などで合わせておいてください）。
- 監視対象の root を取られると、それ以降の記録は信用できません（記録を止める、偽の記録を送る、など）。ただし、それまでにストレージへ送った記録は消せません。記録が止まれば、status に記録の遅れとして出ます。
- 読み直しの順番が来るまでは、ctime などが変わらないファイルの中身は読みません。ctime までごまかされた変更は、最大で `reread_cycle` 回後の読み直し（実行間隔 × `reread_cycle` の時間）まで分かりません。

## テスト

```
python3 -m unittest discover -s tests
```

テスト用のファイルは一時ディレクトリ（`/tmp/fhashes-test` など。環境変数 `FHASHES_TEST_DIR` で変更可）の下に作られ、終了時に消えます。rclone が見つからない場合、rclone を使うテストはスキップします（`FHASHES_TEST_RCLONE` で rclone の場所を指定できます）。

Python 3.6 で動くことは、Docker の `python:3.6-slim` の中で（一般ユーザーとして、PyYAML と rclone の単体バイナリを入れて）同じテストを流して確かめています。root で流すと、読み取りエラーのテストが失敗します（root はどのファイルも読めるため）。

参考（開発環境での計測。1 つのディレクトリに 15 万個の空ファイル）: record は 1 回目約 9 秒、2 回目以降約 8 秒、メモリ約 70MB。log（記録 3 件）は約 5 秒、メモリ約 20MB（rclone を除く）。
